# 架构

## 1. 位置：出口，不是入口

```
             ┌──────────── 模型看到的一切（不变） ────────────┐
提示词 ──► 请求 ──► 模型 ──► SSE 增量 ──► [引擎] ──► 人看到的文本
                                  │
                                  └──► 会话历史（原文，不过滤）
```

引擎是**纯文本函数**：`(chunk, state) -> chunk'`。它没有网络、没有 IO、没有模型调用，甚至不知道上游是谁。这个约束是刻意的——只要引擎不能发起请求，它就不可能多花 token；只要它不碰请求体，它就不可能污染前缀缓存。

## 2. 三段流水

```
push(chunk)
  ├─ 缓冲：拼到 st.buf
  ├─ 切点：safeCut() 找行/句边界
  └─ consume(piece)
        ├─ 行分类：围栏 / frontmatter / 表格 / 空白 / 正文
        ├─ 保护区：splitProtected() 切出行内代码 / URL / 路径 / 公式 / 标签
        ├─ 句子级 pass：emoji、对冲词、破折号
        ├─ 规则：applyRulesOnce() × 最多两轮
        └─ 收尾：tidy()
```

### 2.1 为什么要缓冲

规则会跨 chunk：模型可能输出 `值得注意的` 然后下一帧才给 `是，`。如果在帧边界直接跑规则，就永远匹配不到。

所以引擎攒够 `minEmit`（默认 80 字）之后，回头找**最后一个安全切点**：

- 优先 `\n`（行边界最安全，围栏/frontmatter 识别都靠行）
- 其次 `。！？；…`（句子边界；`^` 锚定规则靠后行断言在句首也能命中）
- 实在没有边界（600 字还没标点，通常是代码或基64）→ 硬切，并把「下一段不是真句首」记进状态，禁用 `^` 规则

不变量：**同一段文本切成任意大小的块喂进去，输出必须与一次性处理一致**（测试 `test/stream.test.js` 用 1/2/3/7/13/64 六种切法锁死）。

### 2.2 行分类状态机

跨 push 保持的状态：

| 状态 | 用途 |
| --- | --- |
| `inFence` + `fenceMark` | ```` ``` ```` / `~~~` 开合，围栏内默认原样 |
| `frontmatter` | 文件开头的 `---` 块，YAML 一个字节不动 |
| `blankRun` | 连续空行计数，删掉整句后最多留一个空行 |
| `comment.{inBlock,inString}` | 块注释 / 字符串状态（code 档用） |
| `atStart` | 是否还没出现过非空行（判断 frontmatter） |
| `midLine` | 上一段是否是硬切（决定 `^` 规则能不能跑） |

### 2.3 保护区

`scan.js` 里一条合并正则按优先级排：

```
围栏 > 行内代码 > URL/邮箱 > Windows 路径 > Unix 路径 > HTML 标签
     > 行内公式 > Markdown 链接/图片 > 引用式链接 > 提交哈希 > 版本号 > 模板占位
```

切出来的受保护片段**原字节拷回**，只有中间的正文段落吃规则。策略是**宁可漏改，不可改错**：认不准就归到保护区。

配套的一条细节：片段之间的空格必须保留。`我们对 \`foo\` 里的 x` 里，"我们对 " 末尾那个空格如果被 tidy 吃掉，就会变成 `我们对\`foo\``，中英混排的读感全毁。所以 `tidy()` 明确不做「去行尾空格」。

### 2.4 规则两轮

规则是有序的，但有序不等于一次到位：

```
值得注意的是，随着人工智能的不断发展，我们改了三处。
       ↑ 先被 filler 规则删掉，`随着…` 才落到句首，opener 规则才认得它
```

所以 `applyRulesOnce` 跑两轮，第二轮没有改动就提前退出。两轮足够覆盖「删前面 → 后面成为句首」这一层，再往上就是语义重写，本项目不做。

### 2.5 注释模式

`mode: "code"` 时整段当源码处理：

1. 逐行扫，带字符串状态（避免把 `"https://a.com//b"` 里的 `//` 当注释）。
2. 只把**注释片段**交给规则，代码片段原样拼回。
3. 注释规则不含任何「删行」「删注释符」的动作，只做词句替换。

所以 `// 注意：首先，进行优化` → `// 优化`，而行数、缩进、`*/` 收尾全都不变——diff 干净，语法安全。

## 3. 为什么 token 与缓存不受影响

| 机制 | 是否被触碰 | 说明 |
| --- | --- | --- |
| 请求体（messages/system/tools） | 否 | 引擎根本没有请求对象 |
| 提示词里的指令 | 否 | 规则不在提示词里，模型不知道有这层 |
| 会话历史 | 否（宿主须遵守契约） | 过滤结果是渲染层产物 |
| 输出 token 计费 | 否 | 模型已经生成完了，我们只改呈现 |
| 前缀缓存 | 否 | 前缀由请求决定，请求没变 → 命中率不变 |

代理模式同理：请求体原样转发（仅去掉 `accept-encoding` 以拿到明文响应），响应侧只改文本字段。

## 4. 性能

单线程、无正则回溯炸弹（所有规则都锚定在短片段上）、无 IO。

实测（Node 22 / 普通笔记本）：

| 场景 | 耗时 |
| --- | --- |
| 100 KB 中文文档，prose 档 | ~120 ms |
| 3 KB 助手回复，chat 档 | < 2 ms |
| 流式：每帧 push（含缓冲与切点搜索） | 微秒级 |

流式路径的开销与帧大小成正比，与全文长度无关（不会每帧重跑全文）。

## 5. 目录

```
src/
├── engine.js     引擎：缓冲、切点、行分类、规则应用、stream/code 两种模式
├── scan.js       保护区扫描 + 代码注释扫描（逐行、带字符串状态）
├── passes.js     非正则的段落级处理：emoji、对冲词、破折号密度、节奏自检、tidy
├── score.js      命中统计与体检分
├── config.js     配置加载、档位推断
├── index.js      公开 API（createTextFilter / humanize / inspect）
├── proxy.js      零依赖 SSE 重写代理
├── mcp.js        零依赖 MCP stdio server
└── rules/
    ├── zh.js  en.js  comment.js
    └── index.js  档位与筛选
```

`bin/deslop.js` 是 CLI；`adapters/` 放各宿主适配器。
