# 安全边界

自动改写文本是有风险的。这一页把风险、护栏和验证方式摊开写清楚，方便你在接入前判断能不能用。

## 1. 硬不变量（每条都有测试锁）

| # | 不变量 | 测试 |
| --- | --- | --- |
| 1 | 保护区内字节零改动（代码、URL、路径、公式、frontmatter、表格） | `core.test.js` 代码块/路径/表格三条 |
| 2 | 流式切块与一次性处理结果一致 | `stream.test.js` 六种切法 |
| 3 | 已有输出不回退（流式只增不改） | `stream.test.js` 单调性 |
| 4 | 不产生空输出（整段被删空则回退原文） | `core.test.js` 回退一条 |
| 5 | 干净文本零改动且幂等 | `core.test.js` 幂等一条 |
| 6 | 注释规则不增删行、不动注释符 | `stream.test.js` 行数断言 |
| 7 | 代码本体零改动（含字符串里的 `//`） | `stream.test.js` 代码档一条 |
| 8 | 越界输入不崩（空串、纯空白、二进制噪声） | `core.test.js` 一条 |

## 2. 风险与对策

### 风险 A：过度纠偏，改成了「假人味」

有人会把「去 AI 味」理解成「加口语词、加语气词、故意写得不工整」。那是另一种假，而且更难改回来。

**对策**：本项目**只做减法**。没有任何规则会新增内容、新增语气词、新增标点。要新增内容就必须知道事实，而事实只有作者有。

### 风险 B：删掉承载语义的从句

「上线时间定在周五，这体现了团队的效率」——后半句承载判断，删掉就是替用户改观点。

**对策**：这类规则标 `safe: false`，只有 `prose` / `all` 档才启用；`chat` 档（对话输出）默认不删。用户也可以 `--disable zh.suffix.uplift` 单条关掉。

### 风险 C：事实漂移

理论上的最坏情况是数字被改。实际上所有数字、单位、路径、版本号都在保护区，规则里也没有任何改数字的动作。

**对策**：规则表里禁止出现数字字面量替换；`--check` 会顺手报出「删改后字数变化」，异常大的变化值得人看一眼。

### 风险 D：代码被破坏

**对策**：两条防线。① `text` 档下围栏代码块整块原样（除非显式 `comments: true`）；② `code` 档下只碰注释片段，注释规则不含删行/删注释符动作。

### 风险 E：把「风格」当成「味」

公文、学术、法律文本本来就该端着写。硬把「兹」「鉴于」删掉是破坏文体。

**对策**：误伤清单（见 `RULES.md`）里明确列了「不拦」的项：四字成语、公文规范用语、单个破折号、无主句。默认档位也不碰标题结构与编号体系（只标记）。

### 风险 F：用户不知道被改了

**对策**：宿主应当把「当前是否启用、什么档位」显示在界面上，并保留原文查看/复制入口（`text()` 的入参就是原文，宿主自己留着即可）。

## 3. 回退策略

| 情况 | 行为 |
| --- | --- |
| 规则把一段删成空 | 逐段允许删空（说明这段全是套话），但**全文**为空时回退原文 |
| 正则抛错 | 单条规则 try 外抛即中止整个引擎？不会：`String.replace` 不抛；若宿主包了 try，异常时请透传原文 |
| 插件加载失败 / `api` 不匹配 | 宿主必须静默降级为不过滤（契约 §4.1.4） |
| 流式没调 `end()` | 会丢最后几十字（缓冲区）。宿主必须 end |

## 4. 怎么验证自己的接入没搞坏东西

```bash
npm test                        # 35 条，含流式一致性与保护区
node bin/deslop.js --check .    # 拿自己的仓库跑一遍体检
```

接入后建议做三件事：

1. **对比同一段文本**：关掉插件与打开插件各生成一次，看代码块/链接/数字是否一字不差。
2. **看流式**：长回复中途是否有「卡住后突然蹦出一大段」（缓冲过大）或「句子被切开」（切点错误）。
3. **看历史**：第二轮对话里模型是否还认得自己上一轮说过的话（如果认不出，说明你把过滤结果写回历史了）。

## 5. 报告问题

规则误伤请附上：原文片段、实际输出、期望输出、规则 id（`--report` 里有）。规则 id 是稳定的，改规则不会改 id。
