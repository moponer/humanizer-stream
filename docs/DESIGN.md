# 设计说明

## 一、0.1 为什么不行

0.1 的定位是「输出侧过滤器」：模型照常写，插件在展示前把 AI 味削掉。它的卖点是不花 token、不动提示词、不影响前缀缓存。这三点确实成立，但它撞上了四个硬问题，而每一个都不是实现细节，是路线问题。

**1. 删除会留下语义空洞。**
「综上所述，X 是一项长期工作。」删掉引导词，剩下的还是一个复述句。真正的毛病在生成阶段：如果模型有一条「最后要给一句总结」的惯性，任何事后删除都只是把这条惯性藏起来。改稿改不出没写过的内容。

**2. 改写等于替作者下判断。**
「不是 A，而是 B」这一句式，有时真的是对立，有时只是修辞。判定需要语义，规则只能给两个选项：一律改（歪曲），或一律不改（漏掉）。0.1 把这类规则标成「只报告不动手」，于是它最想解决的问题恰好落在能力边界之外。

**3. 保护区永远不够。**
代码、URL、模板、表格、引用、数字——0.1 划了很细的保护区，仍然会在「引号里的原话」「Markdown 表格里的对齐行」「JSX 属性的文案」这些地方出错。每加一条保护区，就多一处维护负担，而且没有终点。

**4. 展示与落盘分裂。**
被改的是展示卡，history 与磁盘文件是原文。用户看到的是 A，事后排查看到的是 B，两者不一致。这是最贵的一条：它让「出问题时能复核」这件事失效。

一句话：**在错误的层级上正确的实现，仍然是错误的位置。**

## 二、新设计的三个判断

### 判断一：约束生成，不修正产出

规则进系统提示词，模型从第一句就不写套话。代价是 prompt 变长（chat 场景约 900 字，一次性，不是每轮），收益是根本不需要改稿——写出来的就是要的。

这一步同时解决了缓存问题：规则是系统提示词里的**固定段**，会话内不变，只在建会话时拼一次。0.1 担心的「提示词一变缓存全废」在这条路线上不成立，因为规则根本不变。

### 判断二：规则必须带理由

一条没有 `why` 的规则，半年后没人敢动它，也不知道它是从哪抄来的。所以规则表里每条都要写清：这个特征为什么是 AI 味、改成正例长什么样。

这也顺手挡住了「规则越加越多」的腐化：加一条得说清理由，说不出就不该加。

### 判断三：只报告，不改写

体检器（`check`）只输出分数、命中规则、命中位置。它的三个用途：

- CI 门禁：文案改动里出现套话就拦；
- 交付前自检：写完之后过一遍；
- 抽查存量文案：界面文案、README、错误提示。

它**不是**「绕过 AI 检测」的指标。为了让这句话不被误解，输出里刻意不给「通过/不通过」以外的判断，也不给任何改写建议。

## 三、不变量

这些由测试锁着，改动时先看测试：

1. **确定性**：`writingRules()` 同参返回逐字节相同的字符串（`test/compose.test.js`）。
2. **完整性**：预算不够就整条丢弃，任何一行都不许截半句。
3. **可解释**：每条规则有 `why`，有 `bad` 反例，长度受控（`test/rules.test.js`）。
4. **不误伤**：代码块、行内代码、链接不参与评分；单处半角标点不定罪（`test/check.test.js`）。
5. **零依赖**：没有任何 `dependencies`。

## 四、验证方法

规则有没有用，看两件事：

1. **在真实文本上能不能抓住**：`samples/before-zh.md` 是刻意写成 AI 腔的段落，`samples/after-zh.md` 是按规则重写后的同题段落。
   ```bash
   node bin/deslop.js check samples/before-zh.md samples/after-zh.md
   ```
   前者应该明显超阈值，后者应该接近 0。
2. **在本项目自己的文案上会不会误报**：README、规则表、错误提示都属于「说明性文案」，跑一遍 `--strings` 模式，误报要逐条解释掉，不能靠调阈值糊过去。

## 五、已知局限

- 规则是**语言与文体相关**的：中文规则对英文文本没用，反之亦然。`locale: "auto"` 会同时套两套，代价是误报率上升。
- 结构类规则（加粗比例、列表比例）只是启发式，短文本上不触发。
- 「写得像人」这件事本身没有终点：规则能挡住的是**可枚举的痕迹**，挡不住内容空洞。内容空洞要靠材料与验收，不靠写作规则。
- `check` 的分数是内部质量信号，不同文本类型之间不可比。

## 六、下一步（如果有）

- 按文体细分：公文、技术文档、产品文案的禁忌不一样，现在只有四个粗场景。
- 让体检器输出「这句话为什么被判」，而不只是一个片段——前提是能给出可解释的原因，给不出就不做。
- 规则版本化：宿主注入的规则文本随版本变化，需要能告诉用户「你现在用的是哪一版约束」。
